# stt-worker-spike

Research spike for Phase 3 (local speech-to-text). **This is not application code and must not be integrated before the Phase 2 gate has passed** (project rule 3 in `CLAUDE.md`). It exists to show that the proposed Rust-to-Python process seam works on Windows, and that an unsigned PyInstaller build can run under Smart App Control. Built and run on the laptop on 2026-11-01 (files dated 11:40-11:43).

| File | What |
|---|---|
| `iw_stt_worker.py` | Worker. stdin: binary frames; stdout: JSON lines; stderr: logs. |
| `client.py` | Test client that spawns the worker (or the exe), sends a config frame, five clips and a ping, and prints the replies with timestamps. |
| `iw-stt.spec` | PyInstaller spec generated by `--onedir --collect-all faster_whisper`. |

## Protocol (what the spike proves)

Frame header `<BII` (9 bytes): type u8, seq u32, payload length u32. Types: `1` config (JSON), `2` audio (8-byte u64 capture timestamp in ms + PCM 16 kHz, 16-bit, mono), `3` cancel, `4` ping, `0x7F` shutdown. Replies are JSON lines: `hello`, `loading`, `ready`, `result` (text, audio_ms, proc_ms, avg_logprob, no_speech_prob), `dropped`, `pong`, `error`, `bye`.
Design points that were exercised: stdout is duplicated and fd 1 redirected to stderr so a stray `print` cannot corrupt the channel; a reader thread never blocks on inference (a ping was answered while a transcription ran); a bounded queue of 2 drops the oldest segment with a `dropped` message under overload; the shutdown frame gives exit code 0; pipe close means the parent died.

## Command

```
python -I iw_stt_worker.py                                   # worker alone (needs a config frame on stdin)
python client.py python -I iw_stt_worker.py <model_dir> <wav_dir>
pyinstaller --noconfirm --onedir --collect-all faster_whisper --name iw-stt iw_stt_worker.py   # reconstructed from the generated spec and the build log
python client.py dist\iw-stt\iw-stt.exe <model_dir> <wav_dir>
```

`client.py` takes the worker command line followed by the model directory and the directory with `short.wav`, `mid.wav`, `long.wav` (not in the repo). It sends a `base.en`, 2-thread, beam 1 config with technical hotwords. The original invocations were not recorded.

## Capture-endpoint check

Result: no violation, and no audio device access. The worker consumes PCM bytes from stdin; the client reads WAV files. No WASAPI, `sounddevice`, `pyaudio` or microphone reference exists in any of the three files.

## What the run showed

- Python 3.12.10, faster-whisper 1.2.1, ctranslate2 4.8.4; PyInstaller 6.22.3 (contrib hooks 2026.9), Windows-11-10.0.26200. The build log (`pyi.log`, not copied) has 0 warnings and ends with "Build complete"; total about 70.5 s (the research report says 71 s). `--onedir` output is 238 MB per the research report.
- Cold start of the exe: `hello` at 2.75 s, `ready` at 9.0 s (base.en, first run). Warm run from the venv: ready in about 2.5 s.
- Smart App Control was ON (enforced). Nothing was blocked: the venv's Python-Software-Foundation-signed `python.exe` loaded the unsigned `ctranslate2.dll`, `libiomp5md.dll` and the other pip wheels; the locally built unsigned `iw-stt.exe` ran the full protocol; a copy of it with a `Zone.Identifier` stream (ZoneId=3, mark-of-the-web) also started and ran. The SAC test covered the exe, not every DLL, and SAC is reputation based, so a downloaded or distributed build on another PC may behave differently.
- `o.txt` and `e.txt` (not copied) show one run of the exe where `hello` was printed and the worker then died with `TypeError: a bytes-like object is required, not 'NoneType'` at the config read. The 0-byte `empty.txt` next to them and the timestamps (same minute as the MOTW copy) suggest it was started with an empty stdin; `read_exact` returns `None` on EOF and the code does not handle it. It shows that the exe launched (possibly the mark-of-the-web copy; that link is inferred from timestamps). The crash is a spike bug, not a finding about Smart App Control.
- Not tested: a Tauri `bundle.resources` folder spawned by path, the embeddable-Python route, a clean VM, CUDA.

## Caveats
- The worker hard-codes `language="en"` and `.en` models (English-only interviews were decided on 2026-11-01).
- `upx=True` is in the spec as generated; whether UPX was installed was not recorded.
- Latencies in `result` messages were not saved; see the benchmark table in `../stt-benchmark/README.md`.
