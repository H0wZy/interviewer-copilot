## W: Windows audio semantics (checked against Microsoft Learn and on-machine probes)

**Lens:** Windows audio correctness (WASAPI / Core Audio / COM / MMCSS / Bluetooth / process loopback)

### W1 [blocker] 3.3 Silence-gap synthesis (exact algorithm): Timeline::on_packet, the Situation/Handling table, tests T5/T9, gate M4

- **Draft said:** "Loopback packet QPC positions are essentially 'now' at read time ... so the stream is a continuous timeline anchored at Start"; slack() = 2 ms "absorbs jitter and clock drift"; rows "steady stream: pos within +-2 ms of emitted: nothing" and "packet older than the timeline: drop min(emitted - pos, n) leading frames".
- **Problem:** on_packet reconciles the running sample count (device clock) against the packet's QPC stamp (wall clock) on EVERY packet and edits the PCM whenever they differ by more than 2 ms. Those are two different clocks. Measured on this box (Win 11 10.0.26200, Realtek, default render endpoint, LOOPBACK|EVENTCALLBACK, 1 s buffer, 240 s, nothing playing): device position was contiguous in 23,853 of 23,853 packet transitions, i.e. there was no real hole, yet (a) QPC stamps run 68-77 ppm ahead of the frame count (16.6 ms accumulated in 240 s), so the 2 ms slack is exhausted every ~26-30 s; (b) stamps are engine-processing-time stamps that bunch when the engine is delayed (detrended std 0.15 ms but max |dev| 9.4 ms; two contiguous packets were stamped only 0.77 ms apart). A faithful port of the draft's Timeline fed with that exact packet trace produced 10 mid-stream zero insertions (2.0 to 10.65 ms each, 38.9 ms total) and 3 deletions of real audio (9.23, 7.98 and 4.60 ms = 21.8 ms), including pad+drop pairs (+10.65 ms then -9.23 ms at t=51.94 s). That is ~150 inserts and ~45 deletions per hour on a perfectly clean stream. 'Slack absorbs drift' is false: it only delays the first edit, and with the opposite drift sign the same code deletes speech samples. T5/T9 pass on synthetic data; M4 ('no clicks', exact duration) and downstream VAD/STT see the damage on hardware. The probe thread is managed .NET, but the stamps are written by the engine and the real app will run under at least this much load (browser call + webcam).
- **Evidence:** Learn IAudioCaptureClient::GetBuffer (https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer): pu64QPCPosition is 'the value of the performance counter at the time that the audio endpoint device recorded the device position of the first audio frame in the data packet' (a sampled wall-clock correlation, not derived from the sample clock); _AUDCLNT_BUFFERFLAGS: DATA_DISCONTINUITY = 'not correlated with the previous packet's device position' (device position is the continuity authority). Probe source &lt;scratch>\rev_audio\probe\LoopProbe.cs (contains the Timeline port); 240 s output &lt;scratch>\rev_audio\probe\idle240.txt lines 'device-position continuity', 'QPC-stamp minus frame-count time', 'DRAFT Timeline simulation'. Earlier runs: slope 77.4 / 77.5 ppm (12 s / 8 s), 68.5 ppm (85 s, 3 pads of 2.0-2.4 ms). Mature implementations do not trust stamps: Chromium (https://github.com/chromium/chromium/blob/main/media/audio/win/audio_low_latency_input_win.cc) detects glitches from device position, forces monotonic stamps (last+1 us) and switches to wall-clock stamps when a stamp is >500 ms off (crbug 1439283); libobs ignores stamp deviations under 70 ms (TS_SMOOTHING_THRESHOLD in libobs/obs-source.c); cpal keys on device_position.
- **Proposed fix:** Replace per-packet QPC reconciliation with device-position bookkeeping (frames, drift-free). Keep expected = prev.index + prev.frames. First packet: expected = info.index and NO leading pad (stream starts at its first packet; here the first packet has index 480 with DATA_DISCONTINUITY set and arrives 12.6-12.9 ms after Start). Later packets: gap = info.index - expected; gap > 0 -> push exactly gap zero frames (clamp per finding 2) then the packet; gap == 0 -> nothing (no QPC, no slack, no drops); gap &lt; 0 -> device-position reset: re-anchor and log, never delete PCM. If DATA_DISCONTINUITY is set while gap == 0, fall back to the QPC delta since the previous packet end, clamped. Use QPC only for the no-packet watchdog (finding 3). Keep wall-clock alignment as metadata: t_ms = t0_wall_ms + samples/16 + slewed offset; never insert or delete samples to chase QPC (68-77 ppm is 0.25 s per hour, irrelevant for transcript times). Process loopback reports index 0, so use the contiguous assumption plus QPC fallback there. Tests: T5 replays a recorded trace (contiguous index, +70 ppm stamp drift, +-10 ms stamp excursions; regenerate with the probe) and asserts zero pads and zero drops; keep the 178 ms hole case but assert exactly 8544 zeros from the index gap; M4 unchanged.

### W2 [major] 3.3 capture_loop and Timeline: drop branch, TIMESTAMP_ERROR path, unbounded push_silence(pad)

- **Draft said:** "packet older than the timeline (idle pad overshoot, late read): drop min(emitted - pos, n) leading frames; never duplicates time"; "TIMESTAMP_ERROR: position untrusted: use qpc_100ns() now"; prod.push_silence(pad as usize).
- **Problem:** (1) The drop branch deletes real audio, and the first packet after a quiet stretch is exactly where speech onset lives. It is not an idle-overshoot corner case: it fired 3 times in 240 s of ordinary traffic (finding 1) because stamps bunch. 'Never duplicates time' is bought with lost samples. (2) TIMESTAMP_ERROR only says the stamp is uncertain; substituting read-time 'now' is later than the packet start by the read age (0.5 ms median, 45 ms p99 on this box), which pads and then deletes the following packet. (3) pad is unbounded: a zero/garbage stamp (the exact failure Chromium had to guard against, crbug 1439283) or a >2 s stall becomes push_silence(10^9) into a 2 s all-or-nothing ring, silently desynchronising the stream.
- **Evidence:** Learn _AUDCLNT_BUFFERFLAGS: TIMESTAMP_ERROR = 'The time at which the device's stream position was recorded is uncertain'. Chromium audio_low_latency_input_win.cc: kMaxAbsTimeDiffBeforeSwithingToFakeTimestamps = 500 ms and monotonic fix-up for untrusted stamps. Draft capture_loop line `let q = if info.flags.timestamp_error { qpc_100ns() } else { info.timestamp };`. Simulation output in idle240.txt: DROP events at t=51.94 s, 51.97 s, 183.91 s with flags=0 (no idle pad involved).
- **Proposed fix:** Never discard PCM. If a stamp implies overshoot keep credit = emitted - pos and subtract it from the next gap. TIMESTAMP_ERROR -> treat the packet as contiguous (gap 0), count it. Clamp every synthetic gap to rate/2 (500 ms, Chromium's constant): above that log a warning, bump a `resyncs` counter, push at most one ring-full of zeros and re-anchor (expected = index + frames). Add tests: TIMESTAMP_ERROR packet, stamp = 0, stamp 1 h in the future, 10 s stall.

### W3 [major] 1 (E8), 3.3 situation row 'no packets (idle / silence)', 3.5 LevelFrame.active, 3.9 T9 and M7

- **Draft said:** E8: "Loopback packet delivery while nothing renders is unverified on this driver (Chromium/OBS code suggests packets/events may stop)"; `active` = "real, non-synthesized packets arrived in this hop"; M7 pass = "meter -90, active=false ... answers E8: zero packets or SILENT packets?".
- **Problem:** E8 can be answered now, and the answer breaks the gate criterion. With every render session on the default endpoint inactive (System Sounds, steam, msedgewebview2, Spotify, chrome all state=0), a LOOPBACK|EVENTCALLBACK stream with a 1 s buffer delivered a continuous stream for 240 s: 23,122 wakes, all signalled, 0 timeouts; ~100 packets/s x 480 frames; 0 SILENT-flagged packets; every sample 0.0 (peak 0.0000); device position contiguous. Polling mode behaves the same (399 packets in 4 s). The draft's on_idle never fired (0 idle-pad events). So on this machine idle = an unflagged stream of zero packets: `active` is always true, M7's `active=false` and the UI 'no packets (idle)' label can never be observed, and T9's 'active=false after 3 s of no packets' only exercises a defensive path. Chromium/OBS describe other conditions: Chromium avoids EVENTCALLBACK for endpoint loopback because it 'requires active output audio to trigger the event' and runs a helper render client; OBS adds a 10 ms wait timeout and a 'silent loopback fix'. Learn says event handles are set 'for loopback-enabled streams that are active' (Win10 1703+).
- **Evidence:** Probe runs 8 s, 12 s, 85 s and 240 s (idle240.txt header: 'render sessions on endpoint: 5 ... state=0', 'wakes=23122 (signalled=23122, timed-out=0)', 'silentPk' column all 0, 'maxSamplePeak' 0.0000). Learn IAudioClient::Initialize remarks and Loopback Recording (https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording). Chromium InitializeAudioEngine comment 'Loopback devices capturing from an endpoint device does not support event-driven mode since it requires active output audio to trigger the event'. OBS plugins/win-wasapi/win-wasapi.cpp ClearBuffer 'Silent loopback fix'. wasapi 0.26.0 tests/device/errors.rs: 'a loopback of a render endpoint delivers nothing but zeros' and `assert!(run.frames > 0)`. Learn 'About Power Management': even silent streams prevent audio-device power-down.
- **Proposed fix:** Define silence from level only (rms &lt;= -85 dBFS sustained 500 ms) and rename `active` to `packetsFlowing` = a packet was read in the last 200 ms; keep Timeline idle padding as a watchdog for packetsFlowing=false only. Rewrite M7: run it per endpoint class you will really use (speakers, wired headset, HDMI, Bluetooth) and RECORD packets/s, SILENT count, zero fraction and GetBufferSize; pass = level reaches -90 and recovers, 25 Hz level events continue, no panic, whichever packet behaviour occurs. Make T9 cover both modes (zero packets and no packets). Mark E8 'verified for Realtek / Win 11 26200 (240 s): continuous zero packets'. Keep the silent render helper (default category, never Communications) only as a documented fallback if some endpoint stops delivering.

### W4 [major] 3.3 Silence-gap synthesis: qpc_100ns()

- **Draft said:** "qpc_100ns() = QueryPerformanceCounter * 10_000_000 / QueryPerformanceFrequency (the formula Microsoft documents for pu64QPCPosition)" used for started_q, on_idle and the TIMESTAMP_ERROR path, and compared with Windows-produced stamps.
- **Problem:** The Microsoft formula is mathematical, not a u64 recipe. Measured here QueryPerformanceFrequency = 10,000,000 Hz and the counter counts from boot (1.93 h at probe time vs uptime 1.92 h), so counter*1e7 overflows u64 at 184,467 s = 51.2 h of uptime (49.3 h left when measured); a TSC-rate QPC (2.4 GHz) would overflow after 12.8 minutes. After the wrap, anchor/now are garbage while Windows keeps writing correct stamps, so pos - emitted explodes (see the unbounded pad in finding 2). Release builds wrap silently; debug builds panic into EnginePanic. A dev laptop left running for two days hits this.
- **Evidence:** Learn GetBuffer: '*pu64QPCPosition = 10,000,000 * t / f'. Probe header lines: 'QPC frequency = 10000000 Hz, raw counter now = 70355259178 (2,0 h since QPC epoch)', 'hours left on this machine at this QPC rate: 49,3'; PowerShell: LastBoot 10:41:51, uptime 1.92 h, Stopwatch.GetTimestamp()/Frequency = 1.93 h. 2^64 / 1e7 = 1.8447e12 ticks.
- **Proposed fix:** fn qpc_100ns() -> u64 { let (c, f) = (raw_qpc() as u128, freq() as u128); ((c * 10_000_000u128) / f) as u64 } (or c / f * 10_000_000 + (c % f) * 10_000_000 / f). Add a unit test with c = u64::MAX / 10_000_000 + 1 and with f = 2_400_000_000. Cache the frequency as the draft says.

### W5 [minor] 3.2 Optional activity peek; 3.3 capture_loop sample_os_peak (tick % 2, '~40 ms'); 3.5 osPeakDb; 3.9 M2b/M3

- **Draft said:** IAudioMeterInformation = "the combined peak of all sessions on that endpoint since the previous call, volume-independent per the wasapi docs"; sampled every ~40 ms.
- **Problem:** Microsoft documents a different semantic, and 'volume-independent' appears only in a wasapi doc comment. GetPeakValue always returns the peak recorded during the PREVIOUS DEVICE PERIOD (10 ms here), not 'since the previous call'; the Peak Meters topic defines it as the maximum sample in 'the output stream to the device' during the preceding metering period and says the hardware meter is used when the device has one, which points to a post-volume value. The `tick % 2` cadence assumes 20 ms passes; with the measured 100 wakes/s it runs every 20 ms (50 Hz), and every ~6 ms if another app lowers the engine period (minimum 3 ms here). M2b's premise (volume sweep proves a pre-volume tap via this oracle) rests on a claim nobody verified.
- **Evidence:** Learn IAudioMeterInformation::GetPeakValue (https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudiometerinformation-getpeakvalue): 'recorded over one device period and made available during the subsequent device period. Thus, this method always retrieves the peak value recorded during the previous device period'. Learn Peak Meters (https://learn.microsoft.com/en-us/windows/win32/coreaudio/peak-meters). wasapi 0.26.0 src/api.rs ~1906 (doc comment: 'since the previous call, and are not affected by the volume settings').
- **Proposed fix:** Describe osPeakDb as 'peak of the last ~10 ms device period, sampled'; schedule by QPC deadline (25 Hz), not tick count; keep M3 as shape/timing only; mark volume (in)dependence as unverified and drop it as an oracle in M2b (test our own tap against the master-volume sweep instead). For the peek, 5 samples 20 ms apart cover only half the periods; sample every 10 ms or accept the gaps.

### W6 [minor] 3.3 'Process loopback (capture the browser only)'; 8 S8

- **Draft said:** "Caveats: wasapi 0.26.0 maps include_tree = false to EXCLUDE ... GetMixFormat is unsupported (fixed f32 48k stereo + autoconvert); device position is always 0; it needs no endpoint".
- **Problem:** The listed caveats are correct but incomplete in ways that crash an implementation that reuses Loopback::open: (a) get_buffer_size() returns nonsense for a process-loopback client (wasapi documents values like 3,131,961,357), so `vec![0u8; frames * blockalign]` is ~25 GB and aborts; upstream's own tests cap reads at 192,000 frames for this reason. (b) It needs Windows 10 build 20348+, so add a typed unsupported error. (c) 'fixed f32 48k stereo' is not an OS-fixed format; the app must supply a format and autoconvert. (d) The wasapi doc comment on include_tree is wrong (says false = only the target process) while code and Microsoft use EXCLUDE; the draft's 'always pass true' is right, but do not trust the crate docs here.
- **Evidence:** wasapi 0.26.0 src/api.rs lines ~757-824 (doc: 'get_buffer_size returns huge values like 3131961357 but no error'; code maps false to PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE); tests/device/support.rs MAX_READ_FRAMES = 192_000 with the comment about tens of gigabytes. Learn PROCESS_LOOPBACK_MODE (https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode): minimum client Windows 10 Build 20348; EXCLUDE = streams of the process tree are excluded. Chromium DCHECKs device_position == 0 for process loopback.
- **Proposed fix:** Give process mode its own open path: size the read buffer as min(get_buffer_size(), 2*rate) or a fixed 192_000 frames, never `get_buffer_size() * blockalign` unchecked; supply WaveFormat + autoconvert explicitly; gate on build >= 20348 (new AudioError::ProcessLoopbackUnsupported). Keep initialize_loopback as the single Direction::Capture site so T8 stays at one token.

### W7 [minor] 3.3 Engine thread skeleton; 3.8 classify()

- **Draft said:** `let _reg = en.register_notification_callback(cb);` ; `if wasapi::initialize_mta().ok().is_err() { return; }` ; classify() sends only DEVICE_INVALIDATED / RESOURCES_INVALIDATED / SERVICE_NOT_RUNNING to DeviceLost; "a fresh thread is MTA".
- **Problem:** (1) register_notification_callback returns Result&lt;DeviceEventRegistration, WasapiError> (0.26.0); binding the Result to `_reg` swallows a failure, so FollowDefault never reacts to a default-device change and nothing tells the user. (2) A CoInitializeEx failure returns silently: the UI sees engineGone with no cause. (3) Documented transient codes fall through to the non-retryable Wasapi variant: AUDCLNT_E_ENDPOINT_CREATE_FAILED ('can occur if the endpoint has been unplugged or reconfigured') and AUDCLNT_E_CPUUSAGE_EXCEEDED (engine process pass exceeded its CPU budget; plausible on this 2-core box), so a plug race ends in Failed instead of the backoff. (4) 'a fresh thread is MTA' is imprecise (a thread that never called CoInitializeEx has no apartment, or the implicit MTA if one exists); harmless because the explicit call follows.
- **Evidence:** wasapi 0.26.0 src/api.rs line ~433 (signature returns WasapiRes&lt;DeviceEventRegistration>). Learn IAudioClient::Initialize return table (ENDPOINT_CREATE_FAILED, CPUUSAGE_EXCEEDED). Learn CoIncrementMTAUsage / CoInitializeEx pages.
- **Proposed fix:** match en.register_notification_callback(cb) { Ok(r) => Some(r), Err(e) => { warn!(...); emit a non-fatal event; None } } and, while FollowDefault is capturing without a registration, poll get_default_device_for_role every 2 s as backup. Report CoInitializeEx failure through shared.fail(AudioError::Wasapi{hr, context:"CoInitializeEx"}). Add ENDPOINT_CREATE_FAILED and CPUUSAGE_EXCEEDED (and E_NOTFOUND from Activate) to the DeviceLost group.

### W8 [minor] 3.3 invalidation table (Bluetooth A2DP&lt;->HFP), 9 risk #7, E6, M5; 3.3 rejection of the helper render stream

- **Draft said:** "Bluetooth A2DP&lt;->HFP flip (invalidation inferred from docs, untested)"; Pinned fails after ~5.7 s; the helper silent render stream "interacts with Bluetooth profile switching".
- **Problem:** Microsoft documents a different model for Windows 11 (this box is 26200): A2DP and HFP are unified into ONE render endpoint (Windows 10 had separate 'Stereo' and 'Hands-Free' endpoints, with Stereo audio discarded in HFP mode). Windows picks HFP when an app opens the microphone endpoint or creates an output stream with the Communications category, and resamples to the HFP rate (8 or 16 kHz); a browser call does both. Consequences: the endpoint id is stable across the flip, so Pinned should survive and 'failed after 5.7 s' is not the expected path; the mix format changes (mono PCM16 at 8/16 kHz) on the same id; no document says streams are invalidated, so 'inferred' must stay a hypothesis; the rationale for rejecting a default-category helper stream is unsupported (only Communications category or mic open selects HFP). The 5.7 s budget is arbitrary, no document bounds profile-switch time, and Failed-until-Start costs the answer mid-interview. T3 covers 44.1 kHz and 16 kHz bypass but not the 8 kHz -> 16 kHz upsample path.
- **Evidence:** Learn Bluetooth Classic audio, 'Selection of A2DP and HFP endpoints' (https://learn.microsoft.com/windows-hardware/drivers/bluetooth/bluetooth-classic-audio#selection-of-a2dp-and-hfp-endpoints). Learn Default Audio Endpoint Selection (a newly connected Bluetooth headset becomes the default, wired headphones are preferred over speakers), which also supports the M5 expectations.
- **Proposed fix:** Rewrite the table row: 'Windows 11: one unified BT endpoint; HFP is selected when the mic endpoint is opened or a Communications-category stream exists; expect a format change (8/16 kHz mono PCM16) on the same endpoint id; invalidation unknown -> test M-BT with a real headset'. Add T3 cases for 8000 Hz and 16000 Hz Int16 mono. After the backoff budget keep retrying the SAME target kind every 2 s in the background and show 'Failed - retrying' instead of requiring a manual Start (still never another device kind, so rule 2 holds). Drop the Bluetooth justification for rejecting the helper stream.

### W9 [minor] 3.3 'Thread and COM' (MMCSS 'cheap insurance only'); E1; 3.9 M8

- **Draft said:** "AvSetMmThreadCharacteristicsW(\"Audio\") is cheap insurance only: the 1 s buffer, not MMCSS, prevented loss in the stress test"; M8 = YouTube + webcam page + app, 5 min.
- **Problem:** The stress setup does not cover the scheduling rules that apply in real use. Microsoft's QoS table: a process whose window is minimized or fully occluded is Low QoS (descendants of window-owning processes inherit it, i.e. the Phase 3 Python worker), and Low means 'On battery, selects most efficient CPU frequency'; only 'Audible' processes and MMCSS-tagged audio threads ('Deadline' QoS, Windows 10 2004+) are exempt. This app is capture-only, not Audible, its window will sit behind the call window, and the box is a battery laptop (Win32_Battery present, discharging, Balanced plan when probed). So MMCSS on iw-wasapi is more than insurance, iw-dsp (also deadline-bound) is not registered at all, and M8 must be run occluded and on battery.
- **Evidence:** Learn Quality of Service (https://learn.microsoft.com/windows/win32/procthread/quality-of-service): classification table (Audible = High; Visible: minimized or fully occluded = Low) and levels table (Low, Eco, Deadline). Registry on this box: MMCSS task 'Audio' exists (Scheduling Category Medium, Priority 6), SystemResponsiveness 20. Learn AvSetMmThreadCharacteristicsW: TaskIndex must be 0 on first call; revert when done. OBS registers 'Audio' for its capture thread; Chromium uses 'Pro Audio' + AVRT_PRIORITY_CRITICAL.
- **Proposed fix:** Register iw-dsp with MMCSS 'Audio' as well (task_index initialised to 0, AvRevertMmThreadCharacteristics on exit, failure non-fatal). Optionally opt the process (and the STT child) out of Low/Eco QoS via SetProcessInformation(ProcessPowerThrottling, execution-speed control bit set, state 0). Redefine M8: app window fully covered by the maximised browser, run once on battery and once on AC, record dspBusyPct, discontinuities, droppedFrames.

### W10 [minor] 3.1 Ctl::ListDevices handled in capture_loop via poll_control; 3.2 withPeek; CLAUDE.md capture-thread rule

- **Draft said:** "The capture thread only reads, zero-fills ... and pushes f32" while ListDevices (and its 5 x 20 ms peek) is served from cx.poll_control() inside the capture loop.
- **Problem:** While capturing, Refresh runs EnumAudioEndpoints plus OpenPropertyStore per device (RPC to the audio service, allocations) and, with peek, ~100 ms of sleeps, inside the drain loop. The 1 s buffer prevents loss, but draining and the 25 Hz level stream stall for 100+ ms and the capture thread is no longer the allocation- and lock-free read/convert/push loop CLAUDE.md requires.
- **Evidence:** Draft 3.1 Ctl enum, 3.3 capture_loop comment on poll_control; &lt;repo>/CLAUDE.md machine constraints.
- **Proposed fix:** Serve ListDevices/peek from a short-lived second MTA worker with its own DeviceEnumerator (no COM objects shared across threads), or from the engine idle loop when not capturing; keep only Stop/Shutdown/Start/Dev events in the capture loop.

### W11 [minor] 3.2 Names/IDs ('get_id() ... persisted only as a preference'); Target::Pinned

- **Draft said:** The opaque endpoint id is a sufficient persisted key for Pinned devices.
- **Problem:** Microsoft states the ordinary endpoint id is not stable: an OS or driver update (or uninstall/reinstall) can assign a different id to the same physical device. Windows 11 24H2+ (this box is build 26200) provides PKEY_AudioEndpoint_StableId for exactly this scenario. Without it, a driver update silently turns Pinned into the 'visible fallback to FollowDefault' right before an interview.
- **Evidence:** Learn Endpoint ID Strings (https://learn.microsoft.com/en-us/windows/win32/coreaudio/endpoint-id-strings) and PKEY_AudioEndpoint_StableId (https://learn.microsoft.com/en-us/windows/win32/coreaudio/pkey-audioendpoint-stableid); IMMDeviceEnumerator::GetDevice accepts a StableId from build 26100 and documents E_NOTFOUND.
- **Proposed fix:** Persist { stable_id: Option&lt;String>, endpoint_id } and resolve stable_id first (read it through Device::as_immdevice().OpenPropertyStore(STGM_READ) + GetValue(PKEY_AudioEndpoint_StableId), VT_LPWSTR, may be VT_EMPTY), then endpoint_id; always re-check data flow == Render and state == Active after resolving.

### W12 [minor] 3.4 structural no-mic guarantee, layers 1-3

- **Draft said:** "(Capture device, Capture stream) is an ordinary microphone capture ... Runtime check: the pre-initialize_client direction check (a plain `if`)".
- **Problem:** Not a defect, a missed layer. For FollowDefault, wasapi's Device.direction is just the argument given to get_default_device_for_role (not queried from the OS), so that guard cannot fail on that path; it only bites for get_device(id), which does query IMMEndpoint::GetDataFlow. Windows has a built-in backstop the design cannot reach through wasapi: Initialize with AUDCLNT_STREAMFLAGS_LOOPBACK on a capture endpoint fails with AUDCLNT_E_WRONG_ENDPOINT_TYPE, but initialize_client only sets LOOPBACK when its cached direction is Render, so a bug that hands it a capture device opens the microphone silently.
- **Evidence:** Learn IAudioClient::Initialize return table (AUDCLNT_E_WRONG_ENDPOINT_TYPE). wasapi 0.26.0 src/api.rs initialize_client lines ~1249-1260 (`_ => 0` for Capture/Capture) and get_default_device_for_role ~393-409; as_immdevice() ~719 and as_iaudioclient() ~967 (with the warning never to call Initialize on the raw interface because cached bytes_per_frame would be unset).
- **Proposed fix:** Add an OS-queried check immediately before initialize_client: device.as_immdevice().cast::&lt;IMMEndpoint>()?.GetDataFlow()? == eRender (not the cached value). Optional stronger hardening: call IAudioClient::Initialize yourself with explicit LOOPBACK|EVENTCALLBACK and take IAudioCaptureClient from GetService (~40 lines unsafe) so the OS enforces rule 1; this costs the 'about 0 unsafe' goal, so decide explicitly.

### Confirmed correct by this lens (17)

- LOOPBACK + EVENTCALLBACK in shared mode is supported from Windows 10 1703 (Learn Loopback Recording + IAudioClient::Initialize). Reproduced on this box: Initialize S_OK, 100 events/s with 0 timeouts over 240 s, 480-frame packets, mix 48000 Hz / 2 ch / 32-bit extensible (tag 0xFFFE), device period 10 ms (min 3 ms), exactly one active render endpoint; reproduces the draft's E5 numbers.
- wasapi 0.26.0 sets AUDCLNT_STREAMFLAGS_LOOPBACK only for (Render device, Capture stream, Shared); (Capture, Capture) is an ordinary capture; initialize_client overwrites the cached direction (so the pre-check is needed); bundled loopback.rs and record.rs open the default CAPTURE device; DeviceCollection's iterator unwraps; Handle::wait_for_event maps every non-signalled result to EventTimeout; BufferInfo/BufferFlags field names, WaveFormat accessors, windows 0.62.2 dependency, MSRV 1.85 and release date 2026-10-11 are as the draft states; WaveFormat::new(.., None) gives (1&lt;&lt;ch)-1 = 0x1 for mono.
- SetEventHandle must precede Start; the auto-reset event is created non-signalled (Learn SetEventHandle; wasapi CreateEventA(None,false,false)). A failed Initialize requires a fresh IAudioClient (Learn Initialize remarks), which the retry loop does.
- 1 s hnsBufferDuration with EVENTCALLBACK in shared mode is accepted in practice: GetBufferSize = 48000 frames (1000.0 ms); hns=0 gives 1056 frames (22.0 ms), matching the draft's '22 ms' measurement. Learn's literal text says shared event-driven streams must pass 0 for both (stale; OBS passes 5 s, Chromium 100 ms, cpal arbitrary values). Recommend a runtime assertion GetBufferSize >= 0.5 s with a warn! and bufferFrames surfaced in StreamInfo, since the hns=0 fallback silently loses the glitch protection.
- GetBuffer/ReleaseBuffer handling is correct: whole packet or none, BUFFER_EMPTY -> 0 frames, ReleaseBuffer(0) allowed, same thread, copy-then-release (Learn); wasapi read_from_device releases on DataLengthTooShort (drops the packet and errors, as the draft says) and initialises index/timestamp/flags to 0 so BUFFER_EMPTY is safe; get_next_packet_size returns Some(n) in shared mode.

## R: Requirements compliance and feasibility on the 2-core laptop

### R1 [major] 3.3 Timeline / idle padding; 3.3 invalidation table (sleep/resume not listed)

- **Draft said:** Timeline::on_idle / on_packet pad zeros up to wall-clock QPC position; no cap on the pad size; sleep/resume is not covered anywhere (user asked for it explicitly).
- **Problem:** After system sleep, hibernate or a long scheduler stall the QPC delta between 'emitted' and 'now' can be minutes or hours. If the stream survives the resume, on_idle computes target - emitted = N hours of frames and push_silence tries to write that many zeros. At 48 kHz stereo f32 that is about 1.4 GB per hour: the 2 s ring overflows (dropped_frames explodes), the DSP thread burns CPU on silence, t_ms jumps, and the capture thread (the one that must stay lock/alloc-free) can loop for seconds. If the stream is invalidated instead, resume goes into the 5.7 s reconnect budget, which is also too short right after resume (audio service and BT/USB devices re-enumerate for several seconds). Nothing subscribes to power events (WM_POWERBROADCAST / PBT_APMRESUMEAUTOMATIC) and M1-M9 contains no sleep/resume check.
- **Evidence:** architecture_draft.md 3.3 Timeline code: 'let p = target - self.emitted' with no clamp; 3.3 invalidation table has no power row; 3.9 manual gate has no suspend test. wasapi 0.26.0 read_from_device returns packet QPC as-is (api.rs:2204-2223) so a jump is passed through.
- **Proposed fix:** Clamp every synthesized pad to MAX_PAD (e.g. 500 ms). If the gap exceeds it (or exceeds 2 s), treat it as a stream reset: do not synthesize, re-anchor the Timeline (anchor_q = now, emitted = 0), keep a monotonic t0_ms offset, call FrameSink::on_flush(StreamChange), increment a 'resets' counter and emit a Started/cause=resume or a warn event. Handle push_silence in fixed-size zero chunks from a preallocated static slice (no allocation). Add a unit test T5b: 1 h jump -> bounded output. Add manual gate M10: Sleep 30 s / wake while capturing, expect either automatic recovery within ~10 s or an explicit Reconnecting state, no CPU spike, no panic.

### R2 [major] 3.3 Supervisor and backoff; 3.9 M5

- **Draft said:** Backoff of 6 attempts (~5.7 s) then 'Failed (never auto-recovers)'; Pinned mode never recovers by itself.
- **Problem:** The most likely real-world trigger on this exact setup is a Bluetooth A2DP&lt;->HFP flip: when the browser call opens the headset mic, Windows turns the 'Headphones (Stereo)' render endpoint off and exposes a different 'Headset (Hands-Free)' endpoint (different endpoint ID, 8/16 kHz mono). Profile switching commonly takes more than 6 s, so a Pinned stream fails permanently mid-interview, and a FollowDefault stream can fail if the default has not moved yet. The same budget is too short for resume from sleep, audiosrv restart, and USB/dock re-enumeration. Failing hard in the middle of the call is the worst UX for this product. Retrying the same kind of target (render endpoint) does not violate Rule 2, which only forbids switching to an input device.
- **Evidence:** 3.3 'Reconnecting --budget exhausted--> Failed (Failed never auto-recovers)'; 3.2 Pinned 'Never moves to another device'; 9 risk 7 rates Bluetooth only Med; 3.9 M5 expects 'failed after ~5.7 s'.
- **Proposed fix:** Keep the explicit typed error but make recovery indefinite: after the fast budget, enter a 'Waiting' sub-state of Reconnecting that re-resolves the same Target every 2 s (FollowDefault: new default render; Pinned: same endpoint id becoming Active again) with a visible, persistent banner and an optional sound/title flash after 10 s. Reserve Failed for non-retryable errors (NotARenderEndpoint, UnsupportedFormat after the Os16kMono retry, EnginePanic). For Pinned on a BT A2DP endpoint show a hint 'Headset call mode changes the output device: use Follow default'. Add a gate item that is run with a real BT headset if the user owns one (open question 3), otherwise mark BT as untested.

## Resolution (revise step)

I wrote the final spec to architecture_final.md (about 1,060 lines). It integrates the review fixes and ends with "Appendix: Review log". I accepted 32 of the 35 sub-findings and rejected 3. W12, C5 and R2 are each split into an accepted and a rejected part, so the log has 35 lines for 32 findings. I re-read primary sources wherever a finding conflicted with the draft. I did not touch the repo; git status is unchanged. I checked the doc's tables and diagram widths and ran the new Timeline logic in a throwaway Python port (no files); it behaved as the T5 cases specify.

The main change is the blocker. The reviewer's saved 240 s trace confirms the draft's QPC reconciliation was wrong. Device position was contiguous in 23,853 of 23,853 transitions, QPC stamps ran +68.5 ppm ahead with bursts up to 9.4 ms, and the draft's Timeline fed that trace made 11 pads and 3 deletions of real audio on a clean stream. The new rules for the capture loop are:
- Gaps are detected from device position only.
- No PCM is ever trimmed.
- Holes of 500 ms or less are zero-filled.
- Larger holes trigger a `Resync` reopen.
- `TIMESTAMP_ERROR` or a bad stamp is treated as contiguous.

Other design changes:
- **Idle watchdog:** this machine delivers continuous zero packets when idle (E8), so `active` became `packetsFlowing` and silence is defined by level only. An idle watchdog with credit stays as a defensive path.
- **Reconnect:** recovery now continues indefinitely in a `Waiting` state, retrying the same target kind and showing the typed error.
- **Device handling:** Refresh moved to a short-lived worker thread; pinned devices persist both a stable id and an endpoint id; an unavailable pinned device is never swapped automatically.
- **No-mic guarantee:** an OS-queried data-flow check now sits before `Activate`/`Initialize`, and the source scan is widened and described as a lint.
- **Power and scheduling:** `iw-dsp` joins MMCSS and the process opts out of power throttling (Low QoS applies to occluded windows).
- **Packaging fixes:** TypeScript 6 (no `baseUrl`), the shadcn init flags, the CSP `style-src`, reqwest `json`, the `list_outputs` rename, and the S3/S4 ordering.
- **Environment:** a representative Smart App Control gate, with Plan B first.

Still unverified, and tagged as such in the doc:
- the shadcn `--base radix --preset nova -y` command;
- the `PKEY_AudioEndpoint_StableId` PROPERTYKEY constant (take it from the 26100 SDK header);
- Bluetooth stream invalidation on a profile flip;
- `cpu_threads=1` Whisper latency (not measured; the benchmark would have modified scratch files);
- idle loopback behaviour on endpoint classes other than this Realtek.
